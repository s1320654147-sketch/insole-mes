## 1. 先看结论

这是一个面向 3 到 5 人鞋垫打样和小批量生产工厂的轻量 MES。

它不是母公司旺店通 ERP 的替代品，也暂时不要求与旺店通对接。母公司继续负责电商销售、订单和配货，工厂系统只负责内部生产执行。

系统当前已经从静态 HTML 原型发展为可以在线运行的 Web Alpha：

- 管理端可以登录、查看看板、管理样品单和生产单、查看库存和预警。
- 现场端可以登录、看工单、按工序报工、扫码识别工单、扫码完成物料入库和出库。
- 手机端和电脑管理端共用同一个后端和数据库，手机提交的数据会回流到管理端。
- 系统部署在 Render，并由 GitHub `master` 分支自动触发部署。

当前产品主线已经确定：

```text
样品单/生产单建立
  -> 工单下发
  -> 手机扫码接单
  -> 按工序报工
  -> 原材料批次出入库
  -> 数据回流管理端
  -> 看板、进度和预警
```

不要把项目扩展成重型 ERP。优先把上述闭环做可靠。

## 2. 真实业务背景

### 2.1 公司背景

- 母公司原本是电商型公司。
- 母公司已经使用旺店通 ERP 旗舰版。
- 旺店通主要衔接销售端、供应商供货和配货。
- 新工厂是公司的新业务，也可以理解为相对独立的子公司或生产场地。
- 工厂只负责打样和生产，不直接承担销售工作。
- 当前可以不与旺店通对接，后续是否对接再根据真实业务决定。

### 2.2 工厂规模

- 预计只有 3 到 5 人。
- 同一个人可能同时负责：
  - 原材料入库
  - 备料和生产
  - 打样
  - 工序报工
  - 成品包装
  - 成品进入内部暂存仓
  - 成品出库
- 因此“工人”和“仓库”在手机端不应做成两套割裂的工作台。
- 当前设计已经把 `worker` 和 `warehouse` 的手机端能力合并成“现场端”。

### 2.3 产品和订单特点

- 产品：鞋垫。
- 打样单与生产单必须分开。
- 打样通常为 10 到 20 双。
- 生产单通常不超过 100 双。
- 原材料有保质期，必须按批次管理。
- 生产属于多品种、小批量、流程需要灵活调整的场景。

### 2.4 工厂大致物流/生产路径

```text
原材料采购到货
  -> 按批次入库
  -> 备料/领料
  -> 打样或生产
  -> 工序报工
  -> 检验
  -> 包装
  -> 内部成品暂存
  -> 出库交给母公司或后续环节
```

## 3. 用户最核心的诉求

以下需求是项目的产品判断基准：

1. 保证样品和原材料不丢。
2. 做好库存管理、流程管理和进度跟进。
3. 进货和出货必须有明确记录。
4. 原材料缺货时及时提醒采购。
5. 工厂的每一步尽量可视化。
6. 现场动作不再依赖纸笔和零散 Excel。
7. 工人可以通过手机接任务、看工单、报工和扫码。
8. 管理者在电脑端能够看到手机端提交的数据。
9. 系统界面不需要花哨，但按钮、路径和状态必须清晰。

用户明确不需要：

- 计件工资
- 计时工资
- 复杂薪资绩效
- 销售管理
- 财务总账
- 电商订单管理
- 一开始就做复杂 ERP

## 4. 已经确定的产品决策

### 4.1 做轻量 MES，不再做一套 ERP

原因：

- 母公司已经有旺店通。
- 工厂当前需要解决的是生产执行和现场留痕。
- 销售、财务、供应商协同不是当前系统的职责。

当前系统边界：

```text
负责：样品、工单、工序、批次库存、报工、异常、进度、预警
不负责：销售、财务、电商订单、复杂采购协同、工资
```

### 4.2 暂时不对接旺店通

- 工厂可以先独立运行轻 MES。
- 如果未来需要对接，优先考虑：
  - 母公司给工厂下达生产需求
  - 工厂完工后回传数量和状态
  - 不要一开始同步所有旺店通数据

### 4.3 打样单和生产单分开

打样单重点：

- 样品版本
- BOM/材料调整
- 工艺试错
- 客户或内部确认

生产单重点：

- 计划数量
- 领料
- 工序进度
- 完成数量
- 不良和异常
- 成品入库/出库

建议关系：

```text
一个打样单
  -> 可以有多个样品版本
  -> 某个版本确认
  -> 派生一个或多个生产单
```

### 4.4 原材料必须按批次管理

最低字段：

- 料号
- 物料名称
- 规格
- 批次号
- 数量
- 单位
- 库位
- 来料日期
- 保质期截止日期
- 安全库存
- 供应商（后续补）
- 批次状态（后续补）

规则：

- 每一笔库存动作必须带批次。
- 同一种物料的不同批次不能混成一个库存数字。
- 后续领料建议按 FEFO（先到期先出）推荐批次。
- 临期、过期、低库存需要预警。

### 4.5 报工按工序，而不是只按整单

用户希望“每一步可视化”，因此底层必须按工序留痕。

鞋垫初始工艺路线模板：

1. 备料
2. 裁切 / 开料
3. 成型 / 压制
4. 修边
5. 检验
6. 包装 / 入库

报工最低字段：

- 工单
- 工序
- 本次良品数
- 本次不良数
- 异常备注
- 操作人
- 操作时间

### 4.6 支持部分完工

- 一张生产单可能分多次完成。
- 每次报工只记录本次数量。
- 不允许把“今天做了一半”错误地记成整单完成。

### 4.7 工人和仓库手机端合并

虽然演示账号仍保留：

- `worker`
- `warehouse`

但两者进入手机端后都显示“现场端”，并拥有：

- 看当前工单
- 扫工单码
- 工序报工
- 扫码入库
- 扫码出库

后续如果工厂扩大，再重新拆角色。

## 6. 用户明确的 UI 和协作偏好

这些偏好后续 Codex 必须持续遵守。

### 6.1 UI 偏好

- 内部系统，不需要营销式页面。
- 简洁、清楚、快速找到按钮比“漂亮”更重要。
- 所有按钮的含义必须明确。
- 管理端信息密度可以高，但要容易扫描。
- 手机端要真的适配手机，不是在电脑侧边栏放一个“手机端入口”。
- 不要为了视觉效果增加无用装饰。
- 原型原有 HTML 的直观性要尽量保留。

### 6.2 功能测试交付格式

以后每次新增功能并让用户测试时，必须同时说明：

1. 测试入口或 URL。
2. 使用哪个账号。
3. 先点哪里、再点哪里。
4. 应该看到什么结果。
5. 什么现象代表测试通过。
6. 什么现象代表失败，需要截图什么。

不能只说“已经改好了，你试试”。

### 6.3 Git 和部署偏好

- 日常开发优先在 localhost 修改和验证。
- 用户需要手机测试时才推送到 GitHub/Render。

## 12. 二维码逻辑，务必看懂

### 12.1 两种核心二维码

工单码：

```text
WO|工单号|当前工序
```

示例：

```text
WO|WO-240629-01|成型 / 压制
```

物料批次码：

```text
MAT|料号|批次号|库位
```

示例：

```text
MAT|RM-001|EVA-240615-A|A-01
```

### 12.2 标签页中的二维码内容

工单标签二维码实际编码的是深链接：

```text
https://域名/mobile.html?workOrder=工单号
```

物料标签二维码实际编码的是深链接：

```text
https://域名/mobile.html?batch=MAT%7C料号%7C批次号%7C库位
```

这样做的目的是：

- 用系统内部摄像头扫描时，可以解析链接。
- 用微信、浏览器或系统相机扫描时，也能直接打开手机页面。

### 12.3 正确的扫码入口

工单二维码：

```text
手机现场端 -> 扫工单码 -> 启动摄像头
```

用途：

- 带入工单
- 带入当前工序
- 填写良品/不良/异常
- 提交报工

物料批次二维码：

```text
手机现场端 -> 扫码入库 或 扫码出库 -> 启动摄像头
```

用途：

- 带入物料批次
- 带入库位
- 填写数量
- 提交入库或出库

### 12.4 曾经出现的误操作

用户曾在“扫码入库”区域扫描工单二维码，系统提示：

```text
批次码格式不对
```

原因不是二维码坏了，而是：

- 扫描器成功识别了二维码。
- 当前入口要求 `MAT|...`。
- 实际扫到的是工单链接或 `WO|...`。

这次 UI 改动的目标之一就是减少这种入口混淆。

## 15. 当前已知限制和技术债

### 15.1 二维码图片生成仍依赖公开服务

标签页当前使用：

```text
https://api.qrserver.com/v1/create-qr-code/
```

扫码识别已经本地化，但二维码图片生成尚未本地化。

正式生产前建议：

- 使用本地二维码生成 npm 包。
- 或在后端生成 PNG/SVG。
- 不要依赖公开二维码图片服务。

### 15.2 密码是明文

正式生产前必须：

- 使用 bcrypt/argon2。
- 增加改密码。
- 删除默认账号或强制首次修改。

### 15.3 Token 机制较轻

当前是 Alpha 自定义 Token。

正式使用前需要检查：

- 过期时间
- 签名密钥
- 注销策略
- CSRF/XSS
- 登录失败限制

### 15.4 数据不是实时推送

当前手机提交后写入数据库，管理端需要刷新/重新加载状态。

后续可考虑：

- 定时刷新
- Server-Sent Events
- WebSocket

对于 3 到 5 人工厂，先用低频自动刷新即可，不必立刻上复杂实时架构。

### 15.5 物料“新批次建立”还不完整

当前重点是对已有批次做出入库。

真实使用还需要：

- 新建物料
- 新建来料批次
- 供应商
- 来料日期
- 生产日期
- 保质期
- 初始库位
- 标签打印

### 15.6 库存动作类型仍简化

当前底层主要是：

- `in`
- `out`

未来业务动作应细分：

- 采购入库
- 领料
- 退料
- 补料
- 成品入库
- 成品出库
- 盘点调整
- 报废
- 转库

底层仍可映射为增减库存，但业务类型必须单独记录。

### 15.7 工序推进尚未自动化

当前报工会增加工单完成数量，但还需要明确：

- 何时推进下一工序。
- 一道工序部分完成时怎么处理。
- 多人同时报工怎么处理。
- 返工是否回退工序。
- 完工后是否自动进入检验/入库。

### 15.8 样品二维码流程较弱

目前有样品标签页，但手机端没有完整的独立样品执行流程。

后续需要：

- 样品版本
- 试做记录
- 材料/工艺变更
- 打样结果
- 确认/打回
- 转生产单

### 15.9 源文件编码需持续注意

项目在 Windows PowerShell 中工作，部分命令输出可能把 UTF-8 中文显示成乱码。

编辑规则：

- 文件保持 UTF-8。
- 不要因为终端显示乱码就盲目批量重写文件。
- 先在浏览器和编辑器确认真实文件编码。

## 21. 本次完整沟通时间线摘要

- 用户最初询问生产工厂是不是只能用 MES，不能用 ERP。

### 阶段二：需求收敛

- 用户提出样品不丢、原材料不丢、库存、流程、进度、进出货、缺货提醒。
- 用户无法凭空确定工单状态、报工颗粒度等。
- 通过 ERPNext/Odoo/黑湖等案例确定：
  - 原材料按批次。
  - 打样单与生产单分开。
  - 报工按工序。
  - 支持部分完工。

### 阶段三：参考黑湖小工单

- 用户在小红书和抖音看到黑湖小工单。

3. 它是否让管理者更快知道“现在做到哪、缺什么、哪里异常”？

如果不能回答，暂时不要做。

## 23. 2026-07-04 黑湖专业版参考后的产品化迭代

用户在与黑湖小工单销售人员进行线上演示后，提供了
`黑户小工单功能介绍线上会议逐字稿.md`。该文件只作为产品方向参考，
不代表需要逐项复制黑湖，也不应提交到公开仓库，除非用户之后明确同意。

从会议中确认最值得借鉴的生产执行逻辑：

```text
生产单
  -> 配置工艺路线
  -> 打印工单/工序二维码
  -> 工人用手机扫码
  -> 选择工序并填完成数、良品数、不良数、不良原因
  -> 后端校验，防止超报
  -> 工序达到计划数后推进下一道
  -> 管理端查看实时进度、质量和交期风险
```

本轮明确不借鉴：

- 销售订单
- 采购工作台
- MRP 算料
- 客户和供应商价目表
- WPS 模板导入中心
- 计件工资和复杂绩效
- 大屏、复杂甘特图和重型权限体系

本轮新增或强化的管理端能力：

- 工单筛选：全部、未开始、进行中、已完成、加急、逾期、未来 3 天到期、异常/风险。
- 每个筛选项显示当前数据对应的数量，点击后局部筛选，不刷新页面。
- 工单列表直接展示计划数、完成数、良品数、不良数、不良率、当前工序、交期风险和标签状态。
- 工艺路线使用轻量节点表示未开始、进行中和已完成。
- 工序较多时只在工序区域内部横向滚动，不让整个页面横向滚动。
- 工单详情增加生产执行摘要、工序进度、二维码/标签入口和报工历史。
- 报工历史显示工序、操作人、时间、本次完成数、良品、不良、不良原因和备注。

本轮新增或强化的手机端能力：

- 扫码带入工单后显示工单号、产品、计划数、当前工序、该工序已报数和剩余数。
- 报工表单增加本次完成数量和独立不良原因。
- 数量必须是非负整数。
- 本次完成数不能超过当前工序剩余可报数量。
- 良品数加不良数不能超过本次完成数。
- 不良数大于 0 时必须填写不良原因。
- 提交按钮在请求期间禁用，避免重复提交。
- 提交成功后不整页刷新，更新手机端状态，并在管理端下次拉取数据时回流。

后端数据兼容：

- `reports` 新增 `completed_qty` 和 `bad_reason`。
- 旧报工记录没有 `completedQty` 时，用 `goodQty + badQty` 反推本次完成数。
- 每次提交在服务端再次校验，不能只依赖手机端校验。
- 某工序累计完成达到工单计划数后，该节点完成并推进下一道工序。
- 最后一道工序完成后，工单进入已完成状态。

派生指标规则：

- 无交期：`未设置交期`
- 已逾期：`逾期 X 天`
- 当天到期：`今日到期`
- 未来 3 天内：到期风险
- 未完成且存在不良：进入异常/风险筛选
- 不良率：`不良数 / 已报工完成数`
- 没有有效完成数时：不良率显示 `暂无`

纯计算逻辑集中在：

```text
alpha/public/production-metrics.js
```

自动化测试位于：

```text
alpha/test/report-flow.test.js
alpha/test/production-metrics.test.js
```

运行方式：

```powershell
cd alpha
npm test
```

## 25. 完整沟通记录补充

下面按真实发生顺序补充此前时间线没有展开的细节。它是语义完整的沟通档案，
不是聊天平台逐字导出，但保留了所有会影响产品和开发判断的信息。

### 25.1 最初的 ERP / MES 判断

- 用户最开始从 GitHub 项目 `crbnos/carbon` 切入，询问能否满足原材料库存和生产环节管理。
- 用户曾疑惑工厂管理是否“不能用 ERP，只能用 MES”。
- 结论是 ERP 和 MES 不是二选一：ERP 管企业资源和经营，MES 管现场生产执行。
- 用户补充母公司已使用旺店通 ERP 旗舰版，主要服务电商销售、供应商供货和配货。
- 工厂是新业务或相对独立子公司，只做生产，不负责销售。
- 因此确定先做独立轻 MES，不强制对接旺店通，也不重复造 ERP。

### 25.2 从模糊需求收敛为工厂闭环

- 用户的初始诉求包括样品和原材料不丢、库存、流程、进度、进出货记录、缺料提醒。
- 因为第一次办工厂，用户无法凭空确定工单状态、报工颗粒度等。
- 用户明确原材料有保质期，所以必须分批次管理。
- 打样单和生产单性质不同，必须分开。
- 打样约 10 到 20 双，小批量生产通常不超过 100 双。
- 参考成熟系统后，默认决定报工按工序留痕，同时保留轻量操作方式。

### 25.3 黑湖小工单成为主要参考

- 用户在小红书、抖音看到黑湖小工单，关注微信扫码报工、工单下派、进度、看板和进销存。
- 用户不需要黑湖的计件计时工资，因为工人是统一月薪。
- 用户希望尽量借鉴成熟产品底层逻辑，以降低第一次设计 MES 的难度。
- 用户添加黑湖销售经理并收到介绍视频。
- 视频已拆解为 `docs/heihu-video-notes.md`，提炼出手机入口、工序报工、工单、看板汇总和替代纸笔 Excel。
- 后来用户又提供黑湖线上会议逐字稿，用于校准专业版生产执行流程。
- 用户未来可能提供腾讯会议录屏；届时应分析可实现能力，不要机械照抄 UI。

### 25.4 原型、Web Demo 和 Web Alpha

- 最初使用原生 HTML 快速做了管理端原型。
- 用户指出“手机端入口”不应只是管理端侧边栏菜单，而应是真正适配手机屏幕的页面。
- 用户喜欢原始 HTML 原型的清晰和可视化，要求 Alpha 尽量保持。
- 之后确定双轨：
  - `prototype/` 用于静态演示和讨论。
  - `alpha/` 用于登录、数据库、多人数据和真实手机操作。
- localhost 只供本机开发，不能直接给手机和其他人分享。
- GitHub + Render 的方法论与用户以前的高德地图 API 项目类似，但本项目还多了 Node 服务和数据库。

### 25.5 GitHub 和 Render 部署排障

- GitHub 仓库为 `s1320654147-sketch/insole-mes`，主分支为 `master`。
- 用户第一次 `git push -u origin master` 成功。
- Render Blueprint 曾提示需要付款信息。
- 原因不是“只能有一个免费仓库”，而是 Blueprint 中资源计划配置触发了付款要求。
- 修改 `render.yaml` 把资源计划设为 free 后重新提交。
- 一次 `git push` 因 PowerShell 到 GitHub 443 端口连接失败而中断。
- 浏览器能登录 GitHub 不等于 Git 命令当时的网络链路一定正常；后续重试成功。
- Render 最终创建静态 Demo、Node Alpha 和 PostgreSQL，三项同步显示成功。
- 免费 Web Service 会休眠，首次访问可能延迟。

### 25.6 登录、角色和表单迭代

- 用户验证 Admin 登录可用，但最初没有退出路径，后来已补。
- 用户想测试 Worker，发现 Worker 和 Admin 界面相同，由此推动角色分流。
- 当前 manager 进入管理端，worker/warehouse 进入现场端。
- 用户问管理员本人如果也干活怎么办；当前建议管理动作使用 admin，现场动作使用 worker。
- 长期可以做同一用户多角色，但不是当前 Alpha 的优先级。
- 用户验证新建生产单、新建样品单和样品单编辑基本可用。

### 25.7 物料出入库、标签和扫码

- 用户要求接入物料入库、出库和扫码入口。
- 扫码设计同时支持系统内摄像头和微信/系统相机扫描深链接。
- 工单二维码与物料批次二维码必须分开。
- 工单二维码由工单标签页生成，扫码后进入报工。
- 批次二维码由批次标签页生成，扫码后进入入库或出库。
- 用户曾找不到“标签打印”，因此后续每次测试教程都要给出明确点击路径。
- 原始浏览器扫码只依赖 `BarcodeDetector`，在多款手机浏览器中不可用。
- 改用本地 `qr-scanner` 后，用户真实手机确认摄像头可调用、二维码可识别。
- 用户在“扫码入库”入口扫描工单码时收到“批次码格式不对”，原因是入口类型不匹配，不是二维码损坏。
- 正确规则是工单码用于报工，MAT 批次码用于出入库。

### 25.8 小工厂现场角色合并

- 用户明确总人数只有 3 到 5 人。
- 同一个人会做原材料入库、生产打样、包装、成品暂存和出库。
- 因此 worker 和 warehouse 的现场能力已合并。
- 现场端的主操作统一为扫工单码、扫码入库、扫码出库。

### 25.9 移动端固定操作区

- 用户在手机上发现点击不同扫码入口后，页面会跳到下面的扫码表单。
- 跳转后顶部三个入口和待办/低库存/今日出入库摘要消失，容易不知道当前模式。
- 用户要求红框区域固定不动，只让扫码部分从底部弹出。
- 当前实现：
  - 三个快捷入口和三个摘要指标组成吸顶区。
  - 报工和出入库使用固定底部工作面板。
  - 面板标题明确显示“工序报工”“扫码入库”或“扫码出库”。
  - 面板有关闭按钮和遮罩。
  - 关闭或切换时停止摄像头。
  - 底部导航保留，但不再通过整页滚动打开工作流。

### 25.10 本轮生产执行闭环

- 用户希望月底第一次打样时能够内部跑流程。
- 本轮唯一主线是生产单、工艺路线、标签、手机扫码报工、不良记录、管理端回流和交期视图。
- 已增加状态/交期筛选、生产执行卡片、工序节点、详情历史和质量指标。
- 已增加完成数、不良原因、剩余数、防超报、工序推进和完成状态。
- 没有借本轮机会扩展 ERP、销售、采购、工资或复杂排产。

## 26. 当前版本验收路径

### 26.1 管理端生产视图

入口：

```text
https://insole-mes-alpha.onrender.com/admin.html
```

账号：

```text
admin / admin123
```

步骤：

1. 登录后进入生产工单。
2. 查看顶部八个筛选项和数量。
3. 依次点击未开始、进行中、已完成、加急、逾期、未来 3 天到期、异常/风险。
4. 点击任意工单。
5. 查看详情里的基本信息、工序节点、质量统计、二维码/标签和报工历史。

通过标准：

- 点击筛选不刷新整页。
- 列表数量与筛选结果一致。
- 没有交期、工序或报工时有明确空状态。
- 页面整体不横向滚动。
- 工序多时只在工序区域内部滚动。

### 26.2 手机扫码报工

入口：

```text
https://insole-mes-alpha.onrender.com/mobile.html
```

账号：

```text
worker / worker123
```

步骤：

1. 登录现场端。
2. 点击“扫工单码”。
3. 确认顶部三个入口和三个摘要仍然可见或可回到吸顶位置。
4. 确认底部弹出“工序报工”面板。
5. 启动摄像头，扫描管理端工单标签中的二维码。
6. 确认工单号、产品、计划数、当前工序、已报数和剩余数被带入。
7. 填本次完成数、良品数、不良数；不良数大于 0 时填写不良原因。
8. 提交。
9. 回管理端刷新数据，查看完成数、工序进度、不良数和报工记录。

通过标准：

- 摄像头可启动。
- 二维码带入正确工单。
- 超过剩余数时被拦截。
- 有不良但无原因时被拦截。
- 合法提交只生成一条记录。
- 手机提示同步成功。
- 管理端出现对应人员、工序、数量、不良原因和时间。

### 26.3 扫码入库和出库

步骤：

1. 在手机现场端点击“扫码入库”或“扫码出库”。
2. 确认底部面板标题与选择的模式一致。
3. 扫描物料批次标签二维码，不能扫工单码。
4. 确认物料、批次和库位被带入。
5. 填数量并提交。
6. 管理端查看库存和库存流水。

通过标准：

- 入库增加批次库存。
- 出库减少批次库存。
- 流水包含类型、批次、数量、操作人和时间。
- 切换扫码模式时摄像头不会留下重复会话。
