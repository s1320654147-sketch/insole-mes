## 1. 先看结论

这是一个面向 3 到 5 人鞋垫打样和小批量生产工厂的轻量 MES。

它不是母公司旺店通 ERP 的替代品，也暂时不要求与旺店通对接。母公司继续负责电商销售、订单和配货，工厂系统只负责内部生产执行。

系统当前已经从静态 HTML 原型发展为可以在线运行的 Web Alpha：

- 管理端可以登录、查看看板、管理样品单和生产单、查看库存和预警。
- 现场端可以登录、看工单、按工序报工、扫码识别工单、扫码完成物料入库和出库。
- 手机端和电脑管理端共用同一个后端和数据库，手机提交的数据会回流到管理端。
- 系统部署在 Render，并由 GitHub `master` 分支自动触发部署。

当前产品主线已经确定：

```text
样品单/生产单建立
  -> 工单下发
  -> 手机扫码接单
  -> 按工序报工
  -> 原材料批次出入库
  -> 数据回流管理端
  -> 看板、进度和预警
```

不要把项目扩展成重型 ERP。优先把上述闭环做可靠。

## 2. 真实业务背景

### 2.1 公司背景

- 母公司原本是电商型公司。
- 母公司已经使用旺店通 ERP 旗舰版。
- 旺店通主要衔接销售端、供应商供货和配货。
- 新工厂是公司的新业务，也可以理解为相对独立的子公司或生产场地。
- 工厂只负责打样和生产，不直接承担销售工作。
- 当前可以不与旺店通对接，后续是否对接再根据真实业务决定。

### 2.2 工厂规模

- 预计只有 3 到 5 人。
- 同一个人可能同时负责：
  - 原材料入库
  - 备料和生产
  - 打样
  - 工序报工
  - 成品包装
  - 成品进入内部暂存仓
  - 成品出库
- 因此“工人”和“仓库”在手机端不应做成两套割裂的工作台。
- 当前设计已经把 `worker` 和 `warehouse` 的手机端能力合并成“现场端”。

### 2.3 产品和订单特点

- 产品：鞋垫。
- 打样单与生产单必须分开。
- 打样通常为 10 到 20 双。
- 生产单通常不超过 100 双。
- 原材料有保质期，必须按批次管理。
- 生产属于多品种、小批量、流程需要灵活调整的场景。

### 2.4 工厂大致物流/生产路径

```text
原材料采购到货
  -> 按批次入库
  -> 备料/领料
  -> 打样或生产
  -> 工序报工
  -> 检验
  -> 包装
  -> 内部成品暂存
  -> 出库交给母公司或后续环节
```

## 3. 用户最核心的诉求

以下需求是项目的产品判断基准：

1. 保证样品和原材料不丢。
2. 做好库存管理、流程管理和进度跟进。
3. 进货和出货必须有明确记录。
4. 原材料缺货时及时提醒采购。
5. 工厂的每一步尽量可视化。
6. 现场动作不再依赖纸笔和零散 Excel。
7. 工人可以通过手机接任务、看工单、报工和扫码。
8. 管理者在电脑端能够看到手机端提交的数据。
9. 系统界面不需要花哨，但按钮、路径和状态必须清晰。

用户明确不需要：

- 计件工资
- 计时工资
- 复杂薪资绩效
- 销售管理
- 财务总账
- 电商订单管理
- 一开始就做复杂 ERP

## 4. 已经确定的产品决策

### 4.1 做轻量 MES，不再做一套 ERP

原因：

- 母公司已经有旺店通。
- 工厂当前需要解决的是生产执行和现场留痕。
- 销售、财务、供应商协同不是当前系统的职责。

当前系统边界：

```text
负责：样品、工单、工序、批次库存、报工、异常、进度、预警
不负责：销售、财务、电商订单、复杂采购协同、工资
```

### 4.2 暂时不对接旺店通

- 工厂可以先独立运行轻 MES。
- 如果未来需要对接，优先考虑：
  - 母公司给工厂下达生产需求
  - 工厂完工后回传数量和状态
  - 不要一开始同步所有旺店通数据

### 4.3 打样单和生产单分开

打样单重点：

- 样品版本
- BOM/材料调整
- 工艺试错
- 客户或内部确认

生产单重点：

- 计划数量
- 领料
- 工序进度
- 完成数量
- 不良和异常
- 成品入库/出库

建议关系：

```text
一个打样单
  -> 可以有多个样品版本
  -> 某个版本确认
  -> 派生一个或多个生产单
```

### 4.4 原材料必须按批次管理

最低字段：

- 料号
- 物料名称
- 规格
- 批次号
- 数量
- 单位
- 库位
- 来料日期
- 保质期截止日期
- 安全库存
- 供应商（后续补）
- 批次状态（后续补）

规则：

- 每一笔库存动作必须带批次。
- 同一种物料的不同批次不能混成一个库存数字。
- 后续领料建议按 FEFO（先到期先出）推荐批次。
- 临期、过期、低库存需要预警。

### 4.5 报工按工序，而不是只按整单

用户希望“每一步可视化”，因此底层必须按工序留痕。

鞋垫初始工艺路线模板：

1. 备料
2. 裁切 / 开料
3. 成型 / 压制
4. 修边
5. 检验
6. 包装 / 入库

报工最低字段：

- 工单
- 工序
- 本次良品数
- 本次不良数
- 异常备注
- 操作人
- 操作时间

### 4.6 支持部分完工

- 一张生产单可能分多次完成。
- 每次报工只记录本次数量。
- 不允许把“今天做了一半”错误地记成整单完成。

### 4.7 工人和仓库手机端合并

虽然演示账号仍保留：

- `worker`
- `warehouse`

但两者进入手机端后都显示“现场端”，并拥有：

- 看当前工单
- 扫工单码
- 工序报工
- 扫码入库
- 扫码出库

后续如果工厂扩大，再重新拆角色。

## 6. 用户明确的 UI 和协作偏好

这些偏好后续 Codex 必须持续遵守。

### 6.1 UI 偏好

- 内部系统，不需要营销式页面。
- 简洁、清楚、快速找到按钮比“漂亮”更重要。
- 所有按钮的含义必须明确。
- 管理端信息密度可以高，但要容易扫描。
- 手机端要真的适配手机，不是在电脑侧边栏放一个“手机端入口”。
- 不要为了视觉效果增加无用装饰。
- 原型原有 HTML 的直观性要尽量保留。

### 6.2 功能测试交付格式

以后每次新增功能并让用户测试时，必须同时说明：

1. 测试入口或 URL。
2. 使用哪个账号。
3. 先点哪里、再点哪里。
4. 应该看到什么结果。
5. 什么现象代表测试通过。
6. 什么现象代表失败，需要截图什么。

不能只说“已经改好了，你试试”。

### 6.3 Git 和部署偏好

- 日常开发优先在 localhost 修改和验证。
- 用户需要手机测试时才推送到 GitHub/Render。
- 除非用户明确同意，不要自行 push。
- 即使不 push，也要创建 commit。
- 本次 2026-07-02 用户已经明确同意：当前全部任务完成后 push GitHub。

## 12. 二维码逻辑，务必看懂

### 12.1 两种核心二维码

工单码：

```text
WO|工单号|当前工序
```

示例：

```text
WO|WO-240629-01|成型 / 压制
```

物料批次码：

```text
MAT|料号|批次号|库位
```

示例：

```text
MAT|RM-001|EVA-240615-A|A-01
```

### 12.2 标签页中的二维码内容

工单标签二维码实际编码的是深链接：

```text
https://域名/mobile.html?workOrder=工单号
```

物料标签二维码实际编码的是深链接：

```text
https://域名/mobile.html?batch=MAT%7C料号%7C批次号%7C库位
```

这样做的目的是：

- 用系统内部摄像头扫描时，可以解析链接。
- 用微信、浏览器或系统相机扫描时，也能直接打开手机页面。

### 12.3 正确的扫码入口

工单二维码：

```text
手机现场端 -> 扫工单码 -> 启动摄像头
```

用途：

- 带入工单
- 带入当前工序
- 填写良品/不良/异常
- 提交报工

物料批次二维码：

```text
手机现场端 -> 扫码入库 或 扫码出库 -> 启动摄像头
```

用途：

- 带入物料批次
- 带入库位
- 填写数量
- 提交入库或出库

### 12.4 曾经出现的误操作

用户曾在“扫码入库”区域扫描工单二维码，系统提示：

```text
批次码格式不对
```

原因不是二维码坏了，而是：

- 扫描器成功识别了二维码。
- 当前入口要求 `MAT|...`。
- 实际扫到的是工单链接或 `WO|...`。

这次 UI 改动的目标之一就是减少这种入口混淆。

## 13. 2026-07-02 最新移动端交互改动

用户反馈：

- 手机端顶部有“扫工单码 / 扫码入库 / 扫码出库”。
- 点击后页面会滚到很下面。
- 顶部入口和“待办工单 / 低库存批次 / 今日出入库”消失。
- 到了扫码区域后，不知道自己正在操作哪一种模式。

最新设计：

1. 快捷入口和三个摘要指标合成固定操作区。
2. 页面滚动时操作区吸顶。

## 15. 当前已知限制和技术债

### 15.1 二维码图片生成仍依赖公开服务

标签页当前使用：

```text
https://api.qrserver.com/v1/create-qr-code/
```

扫码识别已经本地化，但二维码图片生成尚未本地化。

正式生产前建议：

- 使用本地二维码生成 npm 包。
- 或在后端生成 PNG/SVG。
- 不要依赖公开二维码图片服务。

### 15.2 密码是明文

正式生产前必须：

- 使用 bcrypt/argon2。
- 增加改密码。
- 删除默认账号或强制首次修改。

### 15.3 Token 机制较轻

当前是 Alpha 自定义 Token。

正式使用前需要检查：

- 过期时间
- 签名密钥
- 注销策略
- CSRF/XSS
- 登录失败限制

### 15.4 数据不是实时推送

当前手机提交后写入数据库，管理端需要刷新/重新加载状态。

后续可考虑：

- 定时刷新
- Server-Sent Events
- WebSocket

对于 3 到 5 人工厂，先用低频自动刷新即可，不必立刻上复杂实时架构。

### 15.5 物料“新批次建立”还不完整

当前重点是对已有批次做出入库。

真实使用还需要：

- 新建物料
- 新建来料批次
- 供应商
- 来料日期
- 生产日期
- 保质期
- 初始库位
- 标签打印

### 15.6 库存动作类型仍简化

当前底层主要是：

- `in`
- `out`

未来业务动作应细分：

- 采购入库
- 领料
- 退料
- 补料
- 成品入库
- 成品出库
- 盘点调整
- 报废
- 转库

底层仍可映射为增减库存，但业务类型必须单独记录。

### 15.7 工序推进尚未自动化

当前报工会增加工单完成数量，但还需要明确：

- 何时推进下一工序。
- 一道工序部分完成时怎么处理。
- 多人同时报工怎么处理。
- 返工是否回退工序。
- 完工后是否自动进入检验/入库。

### 15.8 样品二维码流程较弱

目前有样品标签页，但手机端没有完整的独立样品执行流程。

后续需要：

- 样品版本
- 试做记录
- 材料/工艺变更
- 打样结果
- 确认/打回
- 转生产单

### 15.9 源文件编码需持续注意

项目在 Windows PowerShell 中工作，部分命令输出可能把 UTF-8 中文显示成乱码。

编辑规则：

- 文件保持 UTF-8。
- 不要因为终端显示乱码就盲目批量重写文件。
- 先在浏览器和编辑器确认真实文件编码。

## 21. 本次完整沟通时间线摘要

### 阶段一：MES 还是 ERP

- 用户最初询问生产工厂是不是只能用 MES，不能用 ERP。
- 讨论后确认：ERP 与 MES 不是互斥，但当前小工厂更需要轻 MES。
- 用户补充母公司已有旺店通 ERP。
- 决定工厂系统可先独立，不与旺店通对接。

### 阶段二：需求收敛

- 用户提出样品不丢、原材料不丢、库存、流程、进度、进出货、缺货提醒。
- 用户无法凭空确定工单状态、报工颗粒度等。
- 通过 ERPNext/Odoo/黑湖等案例确定：
  - 原材料按批次。
  - 打样单与生产单分开。
  - 报工按工序。
  - 支持部分完工。

### 阶段三：参考黑湖小工单

  - 替代纸笔和 Excel
